# EvoTool 剩余失败案例分析

日期：2026-10-18。分析对象：此前六次实验中的 EvoTool+Schema，16/30 成功、14/30 失败。数据与代码固定到 `ede2328b8e54eafa6c91e8e0c8e9d42adb238c46`，未宣称分析了远端后续更新。

## 1 已完成的工作和主要发现

完成了 14 题逐题核对、四个条件的轨迹对照、工具定义及代码检查、30 代进化日志分析，以及 40 项离线调用列表检查。没有调用新的模型，没有修改原始预测、评分标准或远端仓库。

最值得继续验证的两个问题是：

1. **规划与调用之间的信息不足。** Planner 不接收工具定义；下游历史摘要不含已调用参数。prompt 中虽然要求避免过度拆分，但模型缺少工具能一次完成哪些需求、此前调用已覆盖哪些需求的直接信息。已有案例与这一解释一致，尚需控制变量验证。
2. **单个错误修好后，整题仍可能失败。** 至少两个案例需要同时去掉冗余调用并修正需求覆盖或参数问题。当前进化采用单模块修改和严格正收益接受；这可能限制某些需要连续修改的路径。不过当前证据只证明多个输出错误共存，尚未证明单模块修改不可能一次修好，也未证明本轮确实发生了这种搜索阻塞。

这些发现目前是对本仓库复现实现的诊断。不能直接写成原论文 EvoTool 的普遍缺陷，更不能在未核对相关工作前宣称新颖性。

## 3 离线最小修改检查

所有操作都在已保存的调用列表上进行，评分器不变。下列结果不能作为新模型的成功率，也不证明模型会自行选择这些修改。

### 3.1 统一规则检查

对全部 30 题使用同一规则：仅保留工具名和参数完全相同的调用的第一次出现。

- 原结果：16/30。
- 离线处理后：19/30。
- 新增成功：bfcl_104、bfcl_58、bfcl_71。
- 原有 16 个成功没有回归。

该规则执行时不读 gold，但它是在看过这批测试失败后选择的，仍是事后诊断。对真实有副作用的工具或明确要求重复执行的任务，不能直接照搬。也不能说 EvoTool 新成绩已经达到 19/30。

## 4 三个优先案例

### A bfcl_58 正确调用已经存在却重复输出

用户要求查两个城市满足条件的酒店。模型先为两个城市各查一次，再把“筛选设施”当成两个子目标，各查一次相同工具。四次调用中已有两条正确且完整的调用；删除重复即通过。

最终 g12-planner 已包含避免过度拆分的要求，仍出现此问题。可验证假设是：单纯增加提醒不足，历史中保存实际 args 或明确维护已覆盖需求可能更有效。先比较同一冻结策略的原历史与含 args 历史，不能直接宣布历史信息就是原因。

### B bfcl_130 任务拆分粒度与工具能力不匹配

任务要求两个博物馆的开放时间和两类票价。工具定义的 details 是数组，一次可以查三项。Planner 把它拆成六个子目标；Caller 按子目标分别生成三个单字段数组。没有完全重复的调用，所以普通去重无效；按城市合并 details 后成功。

代码确认 Planner 只看到 query，Selector 看到工具名、描述和参数键，完整参数 Schema 只提供给 Caller。最终 Planner 提示虽然写了“aligns with the available tools' expected arguments”，却没有实际获得这些定义。

该题适合区分“提示词不够好”与“模块输入信息不够”：对照加强规划提示、提供工具定义、维持原策略。提供工具信息会增加输入 tokens，必须单独计成本。

### C bfcl_149 或 bfcl_29 多个错误需要共同消除

bfcl_149 只有 Music 没有 Theater。单纯去重失败；单纯把一条 Music 改为 Theater 也失败；两个修改结合才成功。bfcl_29 则需要同时去重和处理可选参数。

这支持“整题失败可能由多个独立条件共同造成”。但一次 Planner 改进也可能让下游自动生成全部正确调用，因此不能由手工双修改推导“必须同时改两个模块”。下一步需要冻结策略、分别做单层与组合干预，查看中间轨迹是否分别改善了两个问题。

## 5 代码和进化日志审计

| 已确认事实 | 证据位置 | 能说明什么 |
|---|---|---|
| Planner 输入只有原始任务，工具定义未传入 | src/policy/modules.py 的 run_planner | prompt evolution 无法改变模块签名和数据输入 |
| history 摘要只有 subgoal、tool、output，不含 args | src/policy/agent.py 的 _step_summary | 下游缺少此前调用参数的直接记录；仍有 query/subgoal 信息，不能说完全无记忆 |
| BFCL output 为 None，标记 no_execution | src/policy/agent.py 的 run_episode | 本轮不能验证真实执行反馈、API 报错或返回值依赖 |
| 每个子目标最多选一个工具，可返回 NONE 跳过 | src/policy/modules.py 与 agent.py | 不能声称每个子目标被强制调用；重复是输出行为，不是不可避免的硬约束 |
| 一轮只修改一个模块的 prompt | src/evolve/mutate.py | 不改变状态结构、模块信息流或控制流程；但可多代累积 |
| 默认 mini-batch 的 child 平均 reward 必须严格大于 parent 才接受 | src/evolve/loop.py；config.py accept_on=batch | 不直接接受零收益中间修改；是否阻碍特定案例仍待验证 |
| diversity 的相同 reward 按列表先出现者获胜 | src/evolve/select.py 的 max | 初始策略在平局时占优；不能推断所有淘汰都是平局导致 |

本次 30 代日志：23 次 parent=init，6 次 parent=g0-planner，1 次 parent=g12-planner。11 个 child 被 batch gate 接受，其中 8 个随即未出现在保留种群；最终部署 g12-planner 直接来自 init，只修改 Planner。测试题 ID 与 mutation batch ID 交集为 0。

因此，当前可以提出“有用修改可能不易积累”的候选问题，但还缺少每个被淘汰 child 的逐题 selection reward matrix，无法判断它是否修复了少数有价值的模式、因平局还是其他策略更优而被淘汰。不要把 8 个淘汰解释成 8 个正确修复被错误丢弃。

另一个实现细节：训练诊断将 gold_plan 按工具名压成单个 args 字典；同一工具多次调用时只留下最后一组参数，这可能产生不准确的参数差异提示。该提示只是 Blamer 的辅助信息，不能仅凭代码断言它实际导致了本轮错误归因。

## 6 现有证据的缺口

1. 测试文件保存 plan、最终调用及 Caller trace，但没有完整的逐步 subgoal→Selector→Caller 映射、Planner/Selector 原始输出及每次输入。部分子目标可被跳过，不能把 plan 与调用列表直接按序 zip。
2. 训练日志保存 batch IDs、归因理由、prompt diff 和汇总 reward，但没有完整代表样本轨迹、逐题 child 效果和淘汰策略的 selection matrix。无法追溯“这 14 题被正确归因但改不好”，因为它们未进入训练。
3. 运行仅 1 epoch、单 seed。观察到的失败可能包含搜索预算、模型能力、采样差异、实现和评测口径因素。
4. bfcl_145、56、51、140 应先人工核对语义等价或工具歧义，再确定哪些适合论文主案例。
